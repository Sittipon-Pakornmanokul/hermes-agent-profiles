# Bounded workflows and measurement

## Roll out instructions
1. Confirm scope: advice is not authorization to install; an all-profile rollout includes orchestrator and every explicitly targeted specialist. Read each existing SOUL.md and back it up before targeted edits. Preserve role ownership, user changes and privacy gates. Use the protected Hermes documentation for supported runtime configuration commands.
2. Apply concise shared rules in each profile, then role-specific checkpoints: coder exploration/implementation/tests, reviewer independent diff/dependency checks, designer journey/prototype, critic task/recovery/accessibility checks, operator exact-target retrieval/write/read-back, researcher Discover -> saved Draft -> Verify. Do not force research call limits onto coding or business pagination.
3. Add handoff templates containing decision/goal, original evidence, owned files/targets, acceptance checks, authorized effects, budget, stop conditions, output and receipt paths. Pass relevant artifacts rather than full conversation histories. Reserve delivery capacity and return partial/blocked honestly when a budget expires.
4. Search symbols/paths before broad reads, expand to dependencies when correctness requires it, and retain complete diagnostic evidence locally while returning concise failures and summaries. Preserve completeness/pagination checks. Use deterministic tools for mechanical processing; new reusable software still goes through coder and reviewer.
5. Keep session instructions/toolsets/model routing stable to preserve cache opportunities. Do not claim cache savings or pin endpoints without observed usage. Keep specialists on demand and focus repair re-review on changed areas plus plausible regression paths; never remove independent review to save calls.
6. Distinguish instruction budgets from enforced CLI limits. Report exactly which profiles changed and what artifacts exist. New sessions load new instructions; do not mutate active cached prompts. If testing is explicitly deferred, stop at static verification and state the remaining behavioral/quality tests without launching workers.
7. Before repeating an incomplete implementation handoff, identify the new evidence or concrete dependency that makes another pass productive. Split a blocked cross-layer lifecycle change from a coherent routing fix; escalate the unmet original requirement instead of silently treating a narrower milestone as authorization to stop. Reserve test-environment discovery and build-path inspection for the first checkpoint so repeated workers do not rediscover the same missing prerequisite.
8. Repair and re-review only the demonstrated failing contract when production behavior is correct. Run real integration tests even after static review approves their assertions; a plausible assertion can still misunderstand an endpoint's response shape. Keep the original failing output and the corrected run, and report both without inflating test counts across repeated executions.

## Bounded implementation and review delivery
- Require workers to create a provisional report immediately after discovery and update it after each execution batch; an instruction to write it near the turn cap is not reliable. Preserve native tool-output paths when log redirection is unavailable. An iteration-cap exit is incomplete execution, not a successful report or test failure.
- Pass exact resolved versions, remaining commands, known test prerequisites and prior evidence into repair continuations. Do not spend each continuation rediscovering package selection. Keep independent review, and distinguish dependency-audit cleanliness from full test-suite health.
- Treat unattended approval denials as hard stops for that operation. Do not retry a denied script through another tool or generated file, or strip blocked command parts to continue the same denied operation. Use supported ordinary commands for genuinely separate permitted work; escalate when authorization is needed.
- Separate host-assumption test failures from dependency regressions using the actual failing fixture, executable availability, unchanged-source comparison and targeted old/new-runner evidence. Retain failed full-suite results even if an isolated timing retry passes; never label the entire suite green from the retry.

## Research delivery pitfalls
- Save a provisional draft after sufficient evidence, before optional exploration; reserving verification time does not help if no artifact is delivered.
- Distinguish literal truncation in a saved source from pagination in tool output; rereading a complete file cannot recover absent text. Disclose immaterial gaps and move on. Never switch tools to bypass an approval block.
- Extract exact passages, labels, units, dates/timezones, conditions and provider scope before interpreting consequential claims. Preserve negations and peak/off-peak labels. Label reformatted tables as transcriptions rather than exact quotes.
- Put provider scope in the recommendation itself, not only a distant caveat. Direct-provider pricing is not evidence of reseller billing. Separate documented capability, observed local behavior and proposed experiment.
- Derive call counts from actual records or omit them; model self-reports can miscount. Treat a repaired regression case as a narrow check, not held-out proof of general reliability.

## Lightweight accounting
Start with local per-run receipt templates and a ledger; explicitly label this agent-maintained accounting, not automatic instrumentation. Workers write separate receipts; the orchestrator aggregates serially to avoid lost updates. Record task/run/session IDs, stage, model/provider, actual usage/cache fields, cost/currency, elapsed time, source and accounting scope. Keep unavailable values null and omit prompts, credentials and business content. Separate subscription usage from API billing. Avoid double-counting resumed runs, children and auxiliary calls.

Include failures, corrections, orchestration and independent review in the defined evaluation cohort. Keep acceptance decisions separate from worker claims. A complete cost-per-accepted-task requires complete matching-scope cost evidence and at least one accepted task; otherwise report known subtotals and missing coverage. Fix models/settings during workflow comparisons and include representative and held-out cases before claiming improvement.

## Worker latency (measured 2026-09)
One capped bug fix (10 changed source lines + 1 test) cost ~34 min of coder wall-clock and ~105 tool calls; most of it was re-deriving a root cause the orchestrator had already proven. Changes that materially cut wall-clock without weakening verification:
- **Supply the diagnosis.** Hand off the exact failing line, the traceback and a repro path the orchestrator has already run. Diagnose-then-implement is the largest avoidable cost; keep the worker's verification on the fix, not the hunt. Escalate only when supplied evidence contradicts observation.
- **State caps as HARD.** Advisory budgets overrun (a 25-min advisory became ~29.5 min). Write "HARD cap: N calls / M min" and require an honest partial at the cap.
- **Raw evidence instead of reports.** A 240-line report plus receipt for a 10-line fix is pure latency; ask for the diff hunk and the test summary lines, and read details from the transcript.
- **Expect and anchor approval prompts.** Installs, destructive and nested command bodies trigger a security-scan prompt; one unanswered prompt stalled a run 5 minutes. Keep commands single-purpose, batch a plan into one command where safe, and pre-authorize routine operations (e.g. the project test script) in the handoff. Never strip a blocked command to continue the same denied operation.
- **Parallelize orchestration.** Launch the worker first, then write the review handoff, prep acceptance checks and update records while it runs.
- **One green run per layer.** The worker must not repeat sweeps or acceptance runs the orchestrator performs; independent review still re-verifies, but on the acceptance criteria only.
These are instruction-level changes: report them as applied, not as measured improvement, until a comparable run (ideally with held-out tasks) shows the difference.

## Evaluate code-graph navigation tools
1. Resolve exact repository identity before comparing tools with ambiguous names. Inspect primary README/source, not promotional summaries alone; tool names do not establish implementation or language support.
2. Prefer a local parser-only navigation pilot for code-token reduction. Verify language coverage, outbound calls, embedding/generation defaults, MCP compatibility and index freshness before private indexing. Local storage does not imply local processing, and Hermes ZDR does not automatically govern a separate tool's API calls.
3. Initially expose the index to coder/reviewer only. Query symbols/callers/dependencies for structural questions, then read actual implementation and tests. Keep ordinary search for simple text tasks. Missing edges are not proof of no dependencies; both agents can inherit the same index blind spot.
4. Track branch/worktree and uncommitted changes; stale indexes can hide regressions. Bound graph outputs so navigation does not itself flood context.
5. Compare against targeted search/read, not a straw-man full-repository dump. Count indexing/update costs, query output, source reads, retries and acceptance quality. Treat project-reported per-query compression ratios as examples, not end-to-end savings or verified quality. Do not install multiple overlapping indexes before measuring one.
