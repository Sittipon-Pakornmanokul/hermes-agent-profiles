# Bot visibility and session diagnosis

## Keep a lean user-facing roster
1. Determine whether the request concerns the desktop Bots pane, ordinary Sessions, messaging-platform bots, or scheduled routines. Do not infer that hiding a desktop row disconnects Telegram or disables a schedule.
2. Consult current Hermes Bot Mode documentation and inspect the installed metadata schema. Bots are profiles; removing a profile also removes the specialist's configuration and is not the way to declutter the roster.
3. Keep default and mcp-ops visible and hide other specialist profiles unless the user specifies otherwise. The verified desktop metadata shape is `profile.yaml -> ui_meta -> hermes-bots -> hidden` (boolean), not a model/config routing key.
4. Prefer the supported Hide Bot UI or profile metadata API. Preserve existing metadata and revision fields; do not replace the whole metadata object with only the hidden flag. If an authorized local metadata update is necessary, merge the field and write atomically. Recheck the installed schema before using this fallback.
5. Read back every changed profile's hidden state. Report saved visibility separately from a visually verified desktop refresh. Do not claim the UI has repainted solely because the metadata write succeeded.
6. Explain the scope: hiding is display-only. Specialist CLI/delegation access remains; group membership, mentions and routines may remain active. Do not silently disable those features or delete history.

## Backend capacity errors while browsing settings
1. Separate profile existence, a running desktop backend, and an active agent task. Inspect process metadata without dumping credentials or prompt arguments; a `hermes ... serve` process alone does not prove model calls or task execution.
2. Trace the failing settings request to its profile/backend route, then inspect pool admission, prewarming and cleanup in the installed version. Settings reads can need a backend, and speculative hover prewarming can start one without an explicit task. Do not infer which action started a specific process without logs or a reproduction.
3. Check the supported Advanced settings and persisted device-local pool preferences before proposing code changes. Useful source anchors are `pool-limits.ts`, `prewarmProfileBackend`, `startPoolIdleReaper` and `getEnvVars`; locate symbols rather than relying on fixed line numbers. Distinguish non-primary pool capacity from the primary desktop backend when counting processes.
4. Verify defaults, clamps, cleanup cadence and what refreshes activity. The inspected implementation used a ten-minute idle default, a one-minute minimum and periodic cleanup; recheck these values on the installed version. A connection/activity-based idle timer is not a task-finished hook, so lowering it does not establish immediate shutdown after work.
5. Distinguish bounded CLI delegation (`hermes -p PROFILE chat -q '...'`) from desktop `serve` processes. A task-scoped CLI worker does not require a persistent desktop backend for the same profile. Do not change delegation machinery merely to address a desktop pool issue.
6. Report supported configuration separately from desired lifecycle changes. Treat restart and larger capacity only as optional temporary mitigations, not resolution. For a proposed fix, require profile-settings browsing at the configured limit without interrupting active work, and verify startup and release behavior separately. Do not label an untested timeout adjustment or proposed patch as a working fix.

### Implementation handoff and acceptance
1. Split settings routing, speculative startup and safe release into independently verifiable checkpoints. Give coder the first bounded slice plus the overall acceptance matrix; reserve a separate lifecycle pass when release crosses Electron, renderer and backend boundaries. A partial startup patch must not be reported as completed on-demand execution.
2. Trace both connection-registry and legacy request dispatch before choosing the routing seam. A profile-aware endpoint can exist while the actual desktop request bypasses its shared-backend resolver. Preserve connection identity independently from target profile; test explicit local pins, profile overrides and remote connections rather than assuming a local source guarantees a local destination.
3. Require key list/write/delete/reveal to resolve to the same intended profile. Verify with dummy credentials in temporary homes across A→B→A. For asynchronous settings actions, keep status polling on the process that owns the action; a broad settings allowlist can move the initiating request without moving its poll.
4. Require dedicated tests of speculative startup disabled, explicit invocation enabled and retained warm-mode behavior. Check consumers, typed constants and hand-written mocks when extending a shared preference shape; passing only the preference parser tests does not validate its renderer consumers.
5. Specify safe release as an acceptance contract, not an assumed implementation: protect active turns, tools, dependent background work and in-flight requests; fail safe when activity is unknown; test shutdown versus acquisition races and intentional-close reconnect behavior. An activity snapshot or busy flag alone does not prove an atomic safe-to-stop decision.
6. Inspect the actual diff and logs before independent review. Distinguish pure routing tests from real backend isolation, process-cap integration and packaged-app validation. Keep source implemented, checks passed, review accepted, package built and running app updated as separate delivery states; do not replace or restart the user's active app merely to make the final report sound complete.

## Sessions that appear to return
1. Obtain the exact session title or ID and whether it appears in Sessions, Bots or a chat tab. A recreated replacement and an undeleted conversation require different diagnoses.
2. Read the relevant profile's session database in read-only mode. Inspect its actual schema before selecting fields; compare session IDs, titles, source, hidden/archive state and end state. Avoid exposing message content when metadata suffices.
3. Distinguish canonical Bot Chat behavior from ordinary sessions. Bot Mode maintains a canonical chat; reopening a bot after its chat is retired can create a replacement. Do not assume the same mechanism explains ordinary sessions returning.
4. If records are absent from the correct database but still visible on screen, report that deletion persisted locally and investigate frontend cache/connection ownership next. If records remain, inspect the deletion response and session ownership before assigning a cause. An ended timestamp alone does not prove deletion.
5. Keep speculative causes labeled as hypotheses. Do not prescribe backend restarts, database deletion or repeated destructive cleanup without evidence. Do not promise that hiding a bot prevents canonical-chat creation.

No resolved fix for ordinary-session reappearance was established in the reviewed workflow; use this diagnostic procedure rather than presenting stale-cache or active-connection explanations as confirmed causes.
