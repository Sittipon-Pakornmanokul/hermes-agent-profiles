# Evidence-backed model selection for role profiles

## Standing user requirements
- Only `default` may authenticate directly to Codex/OpenAI. Never log specialist profiles into these providers, copy/link default OAuth files, expose default credentials through a proxy, or use direct Codex/OpenAI as a specialist repair fallback. Specialists retain their separately authorized OpenRouter access; an OpenAI model through OpenRouter is not direct OpenAI authentication. If a specialist's compliant route is blocked, report the blocker rather than borrowing default's authentication.
- Use the named `code-reviewer` profile for independent source-code, diff, security and test review (not the former `reviewer` ID). Route screenshots/images and visual UX review to `ux-ui-critic`; split mixed reviews and integrate both reports. These are orchestrator handoff rules, not automatic vision-tool redirection. Keep screenshot-only evidence distinct from tested browser behavior.
- Preserve separate orchestrator, implementation, review, design and critique responsibilities; keep each profile's skills lean.
- Keep only default and mcp-ops visible in the desktop Bots roster; preserve specialist profiles for delegated work. Treat roster hiding, session deletion, routine disabling and profile deletion as different operations, never interchangeable cleanup actions.
- Prefer on-demand specialist execution with release after work completes. Preserve normal multi-profile browsing: do not present restarting the desktop or raising process limits as the proper fix for settings exhausting backend capacity. Check existing lifecycle controls first, distinguish idle timeout from task completion, and obtain authorization before changing limits or implementing lifecycle behavior.
- Prefer supported configuration and evaluation of the official localhost dashboard before proposing a custom desktop fork or new mission-control website. Explain which layer owns the defect and separate configuration mitigation from a code fix. Evaluate maintained self-hostable interfaces against the actual delegation workflow before building a replacement; local hosting alone does not establish lifecycle correctness or privacy.
- Avoid Anthropic models for design work, including design-profile auxiliary calls. Do not treat a skill named after a vendor as a model dependency.
- Do not recommend Gemini models: the user has explicitly excluded them over factual-reliability concerns. Preserve this exclusion when selecting research candidates; do not quietly reintroduce Gemini through auxiliary defaults or model fallbacks.
- Require ZDR for all OpenRouter calls, including auxiliary calls. Prefer cheapest eligible endpoints when price-first routing is requested; never relax privacy to make a model work.
- Explain UX decisions in plain language for a user without design experience. Prioritize user journeys and overall website flow over attractive isolated screens.
- Recommend models with evidence appropriate to the task; distinguish measured results, informed judgment and untested hypotheses.
- Treat low cost as a constraint, not the primary selection criterion: the user requires accurate, reliable research. Compare cost per verified usable deliverable, including retries and corrections, rather than token prices alone.
- Minimize profile proliferation. Add a specialist for a distinct recurring responsibility or permission boundary, not for every task or validation step; reuse existing roles before proposing another validator.

## Procedure
1. Identify the role, modality needs, cost sensitivity, excluded vendors, privacy requirements and exact authorization. A request for a recommendation is not permission to switch. Change only authorized profiles.
2. Read current profile settings and consult the protected hermes-agent skill for supported commands. Verify exact model IDs and input modalities against the live provider catalog. Do not infer that a model variant exists from another variant's name.
3. For benchmark-based requests, retrieve primary leaderboard data and methodology. Distinguish interface-generation preference rankings from real-user task success, behavioral prediction and end-to-end journey quality. Record tested model versions, harness and evidence gaps. Do not present scores from one category as universal UX ability or compare unrelated benchmarks numerically.
4. Propose a model suited to the role and budget. For research comparisons, prefer a live independent head-to-head evaluation over vendor marketing or cached search snippets. Identify exact variants (Flash versus full models), effort settings and benchmark/index versions; refreshed leaderboards can differ from older articles. Explain reliability indices rather than presenting them as accuracy percentages, and do not infer statistically meaningful superiority from small gaps without uncertainty estimates. Distinguish closed-book knowledge reliability, document reasoning, agentic execution and source-grounded citation accuracy: none alone establishes trustworthy research reports. Label weighted benchmark task cost separately from provider token prices and the user's actual ZDR-endpoint bill. A different-family critic can provide another perspective, but neither model diversity nor agreement proves correctness. Avoid repeated confident recommendations unsupported by comparative evidence.
5. Apply authorized configuration through `hermes -p PROFILE config set KEY VALUE`, not hand-edited YAML. Create new specialists with `hermes profile create PROFILE --no-skills --no-alias`, install only the role's needed skill directories with their supporting files, and preserve bundled-reseeding opt-out. Copy only an explicit allowlist of required provider secrets, never a business-operations profile's entire `.env`; copying the whole file can grant unrelated credentials even when MCP configuration is absent. Keep credential values out of tool output and use restrictive file permissions. Update main and explicitly pinned auxiliary models together so the old vendor is not left active in visual analysis or disabled title settings. Preserve role instructions, skills and privacy unless changes are authorized.
6. Verify routing in the installed runtime before trusting a config-write success. For price-first OpenRouter routing, the verified configuration path was `provider_routing.sort = price`, with `provider_routing.data_collection = deny`. An unknown-key warning can reflect registry/runtime drift: inspect the actual reader rather than blindly accepting a suggested similarly named key. Recheck this on other versions.
7. Treat no-training and ZDR as distinct policies. Account-wide ZDR covers OpenRouter calls under that account; main-agent routing does not automatically propagate to auxiliary calls. For explicitly configured auxiliary routes, pass `extra_body.provider` with `sort: price`, `zdr: true` and `data_collection: deny`. Do not assume an arbitrary main-agent ZDR config key is supported. Price sorting prioritizes eligible endpoints; it does not guarantee minimum final cost across cache, token-mix and availability differences.
8. Unless the user explicitly defers testing, run a fresh profile session with a harmless real tool call, then inspect its persisted tool result and read back configuration. When asked to roll out first and test later, perform only installation/static consistency checks, do not launch behavioral benchmarks, and label runtime behavior and savings untested. Report separately: configuration verified, model connectivity verified, tool execution verified, vision tested or untested, and domain quality evaluated or unevaluated. A printed success token is evidence of execution, not proof of provider privacy by itself.
9. If an optional auxiliary request fails due to ZDR, preserve the restriction. Verify an eligible explicit route or disable the optional feature and disclose that tradeoff. Do not document an unverified retry as a working fix.
10. Report exact changed profiles/models, routing policy, test results and remaining limitations. Explain that new sessions load the changes. Do not claim benchmark-equivalent performance from a short smoke test.

## Workflow optimization rollout
For cross-profile cost optimization, follow [Bounded workflows and measurement](references/workflow-efficiency.md). Distinguish proposed changes, saved instructions, runtime enforcement and measured improvement. When the user authorizes an all-profile rollout, enumerate every target and apply role-specific rules rather than updating research alone. Preserve independent review and exact-target business read-back; do not add agents or weaken ZDR to save tokens.

## Read-only profile audit
- Inspect both raw YAML and the installed runtime's read-only merged configuration: absent keys can enable background self-review and curator behavior, and named profiles do not inherit default-profile overrides. Distinguish enabled configuration from evidence that a background job actually ran.
- Treat Doctor's tool-availability checks as prerequisite checks, not successful execution: a keyless web backend can appear available while extraction returns HTTP 403. Catalog membership likewise does not prove model inference or ZDR endpoint availability.
- Verify account-wide ZDR separately from per-request routing. Missing local ZDR flags are an enforcement/evidence gap, not proof that retention occurred; `data_collection: deny` alone does not establish ZDR. Check every applicable auxiliary task, including newly added runtime defaults.
- Separate actionable dependency/config warnings from intentionally unused providers and integrations. Do not bulk-install optional packages or grant Full Disk Access merely to clear Doctor warnings; preserve least privilege.

## Bot visibility and session lifecycle
For roster cleanup or sessions that appear to return after deletion, follow [Bot visibility and session diagnosis](references/bot-visibility-and-sessions.md). Preserve specialist profiles and histories unless deletion is explicitly authorized; inspect persisted state before claiming that a UI action failed.

## Residue cleanup after skill/profile trimming
Treat these as pitfalls, not routines — run only when the user authorizes cleanup:
- Empty category dirs holding only DESCRIPTION.md are leftover scaffolding after bundled-skill removal. Delete them only after confirming the profile's `.no-bundled-skills` marker exists (without it, installer/update seeding can re-create them); back up first (tar or `cp -R`), then removal is safe and permanent.
- NEVER run `hermes skills opt-out --remove` on a curated profile: besides writing the marker it deletes still-present unmodified bundled skills (e.g. hermes-agent). Plain `opt-out` (no `--remove`) is the non-destructive form.
- `hermes profile list` omits profiles lacking config.yaml, but `hermes profile delete NAME -y` still finds and removes such residue. The delete output does not state identity-purge status, so follow with `hermes profile purge-identity NAME` and confirm it reports success (observed idempotent: a retry after a sanctioned delete still returned "identity purged", exit 0).

## Interface migration and preserving profile data
For a move from Desktop to dashboard or a clean reinstall, follow [Profile-preserving migration](references/profile-migration.md). Inventory and back up before removal; preserve named-profile data and privacy policies separately from application code, generated artifacts and desktop-local state.

## Research and RAG role allocation
1. Separate evidence work from implementation: research owns source discovery, assessment, cited synthesis, corpus criteria, provenance, metadata, freshness rules and source-backed evaluation questions; coder owns ingestion/retrieval/application implementation and tests; reviewer checks implementation and test validity; default coordinates and checks consequential claims against original sources. Route authorized business-service publication through mcp-ops.
2. Do not create a dedicated research validator by default. Use a fresh-session evidence-audit assignment with the original question and source artifacts; require unsupported claims, contradictions and evidence gaps to be identified. Separate context is not independence of model blind spots, and an audit verdict does not replace measured RAG evaluation.
3. Before selecting a cheap research model without comparative evidence, evaluate candidates on identical representative assignments: a tools comparison, a software/methodology investigation and RAG source preparation. Check source quality, citation entailment, factual accuracy, freshness, uncertainty, contradictions and provenance. Choose the cheaper candidate only after it meets the quality standard; do not describe an unrun evaluation as completed or a catalog listing as an accuracy benchmark.
4. Require inspected sources for consequential factual claims, explicit uncertainty for unsupported claims, and primary-source rechecks for time-sensitive claims. Escalate consequential recommendations or difficult synthesis rather than applying premium-model cost to every extraction step.
5. Build source-backed RAG evaluation questions before tuning retrieval. Inspect retrieval misses, unsupported answers, citation correctness, abstention when evidence is absent, latency and cost; keep held-out checks separate from tuning examples. Model agreement alone is not an evaluation result.
6. Check embedding services, vector stores and document storage independently for privacy, access control and update/deletion behavior; model-provider ZDR does not cover those components.

## UX design and critique gate
Require user goals, information architecture and a low-fidelity end-to-end journey before visual polish. Give the critic original requirements and actual artifacts in a separate session; avoid supplying only the designer's conclusions. Findings should include location, observed evidence, user impact, severity, proposed fix and retest criterion. The designer revises; the critic rechecks. Keep critique report-only unless authorized otherwise.

Distinguish specification review from browser interaction testing. Screenshots cannot validate keyboard behavior, recovery or mobile responsiveness. Include loading, empty, error, backtracking and interrupted-task paths. Do not fabricate research, personas, task completion metrics or usability results. Recommend representative-user testing and actual post-launch metrics rather than claiming optimized UX from model agreement.
